# Momentum to Raindance

Three .NET 8 Frends tasks for Momentum invoice export with progress, fetch receipts, permanent invoice identities, and delivery evidence in PostgreSQL. Uses Npgsql 8.0.9 and schema `004_database_checkpoint`. No Frends KV/shared state is required. This release changes task bindings and must be deployed with its matching migration.

- **Fetch Ledger Note Accountings** takes API and database settings, reads the database cursor, traverses every page, and registers a durable fetch receipt. It returns prettified JSON in `ResultFile`, its `FetchId`, and an informational starting `LastLocalId`. There is no checkpoint input.
- **Convert GraphQL Result** takes the unchanged JSON and matching `FetchId`, plus the same database/source. It checks receipt integrity and current database progress, then validates and durably reserves previously unseen `(SourceSystem, ledgerNote.id)` identities **before returning bytes**. Result fields include `ResultFile`, `Filename`, `NodeCount`, `SkippedInvoiceCount`, `DeliveryId`, `ContentSha256`, and the proposed `LastLocalId`. Do not filter or reformat Fetch's JSON.
- **Confirm Invoice Delivery** records evidence after the external file writer succeeds and advances the database cursor in the same transaction. No KV write follows. Confirmation is idempotent with identical source, fingerprint and evidence; the writer must not be retried automatically.

Conversion `ResultFile` is still `byte[]`, already ISO-8859-1/Latin-1 encoded with fixed-width spaces and CRLF. `Filename` is a string in `300K24_yyyyMMdd_HHmmss.txt` format. Pass these to the existing file writer's File and Byte content inputs respectively, using RAW mode and overwrite off. Do not re-encode. On `NodeCount == 0`, skip the writer and confirmation: output bytes, filename, delivery ID and hash are empty, and validated progress is already committed in PostgreSQL. This includes historical/delivered duplicates and intentional empty/rounding-only events. An empty feed leaves progress unchanged.

An unresolved reservation blocks Fetch and Convert for the whole source and never expires or automatically releases. A timeout or restart cannot reset database progress or authorize another file. Confirmed/historical identities are never re-exported through this workflow. This provides at-most-once admission, **not a distributed exactly-once delivery guarantee**: manually copied or cached output and writer retries remain unsafe. A recorded delivery means file delivery, not Raindance import.

Before first production use, run the separate offline migrations, reconcile and seed previously delivered invoice IDs, register/activate a permanent source, and configure the same database/source on all three tasks. The same login can perform setup and runtime work; a separate restricted login is optional. Follow the [numbered first-time setup](../database/README.md); no user creation is required. For an existing installation, pause execution, migrate to 004, reapply optional restricted grants, update task bindings, and remove KV steps. Migration starts the new cursor at zero; complete replay suppresses existing identities safely. Do not reseed, reactivate, or change the source. There are no Frends-time migrations or untracked production mode. Keep tracking history permanently, with backups and restore reconciliation. The local CLI is diagnostic preview only and its output must not be delivered.

API and database settings accept JSON, manual configuration, or canonical **HcpVault**, currently backed by Infisical. Use separate secrets; production connections require verified TLS. All tasks support cancellation and fail by throwing, without returning partial output.
